This site ships no framework to the browser. Not a small framework — none.
Every interactive piece on it is a short vanilla TypeScript module that Astro
bundles, and the total client-side JavaScript is a few kilobytes compressed.

That was a constraint I set at the start, mostly to find out whether the things
I actually wanted were hard without a framework. Almost none of them were.

## What actually needs JavaScript

I wrote down the interactions I wanted before writing any code, which turned
out to be the useful part:

- A theme toggle that never flashes the wrong colours on load.
- Scroll-triggered reveals that degrade to "just visible".
- A nav indicator that slides between sections.
- A pointer-tracked spotlight on cards.
- A generative hero that pauses when it is off screen.
- A mobile menu that traps focus properly.

Six features, six small modules, one shared `onReady` helper that re-binds
everything after a view transition. The largest is the hero canvas at 3.7 kB
before compression — 1.8 kB over the wire — and most of that is the
simulation, not the plumbing.

The list started longer. A command palette was on it, and it got built, and it
worked — and then it came off again, because a personal site with six pages
does not need keyboard-driven search. Deleting it removed 534 lines and made
the header read as a masthead instead of an app toolbar. Knowing what the thing
is includes knowing what it isn't.

## The theme flash is a rendering problem, not a state problem

The only piece of blocking script on the page is this, inlined in `<head>`:

```js
(() => {
  const stored = localStorage.getItem('theme');
  const dark = stored ? stored === 'dark' : matchMedia('(prefers-color-scheme: dark)').matches;
  document.documentElement.dataset.theme = dark ? 'dark' : 'light';
  document.documentElement.classList.add('js');
})();
```

It has to be inline and it has to be blocking, because the alternative is a
frame of light theme in front of someone who asked for dark. Every other script
on the site is deferred or module-typed.

The `js` class is the other half: all the reveal animations are scoped under
it, so if scripts fail to run, nothing is stuck at `opacity: 0`. Progressive
enhancement is easy to claim and easy to get wrong in exactly this way.

## Fonts, subset and self-hosted, with no CDN

Astro's font pipeline resolves families out of locally installed
`@fontsource-variable` packages, subsets them, and emits metric-matched
fallback metrics automatically:

```js
fonts: [
  {
    provider: fontProviders.npm(),
    name: 'Newsreader Variable',
    cssVariable: '--font-display',
    weights: ['200 800'],
    subsets: ['latin'],
    fallbacks: ['Iowan Old Style', 'Palatino', 'Georgia', 'serif'],
    options: { package: '@fontsource-variable/newsreader' },
  },
];
```

Three consequences worth the setup cost. The build never talks to a font CDN,
so it works offline and cannot break because someone else's service did. The
served files are latin-subset variable fonts rather than full families. And the
generated fallback has matched metrics, so there is no layout shift when the
webfont lands — the fallback occupies the same space.

## Social cards rendered at build time

Every page and post gets its own Open Graph image, generated during the build
by Satori and rasterised with resvg. The route is a static endpoint that
enumerates every page, so adding a post adds its card with no extra work:

```ts
export const getStaticPaths = async () => {
  const posts = await getCollection('writing');
  return [
    { params: { route: 'home' }, props: { title: profile.name } },
    ...posts.map((post) => ({
      params: { route: `writing/${post.id}` },
      props: { title: post.data.title, kind: 'Writing' },
    })),
  ];
};
```

Satori takes a subset of CSS and a font buffer and returns SVG; resvg turns
that into a PNG. It has real limits — flexbox only, no grid, no external
images — but for a typographic card those limits are not binding.

## What the numbers came out at

From an actual production build, all figures gzipped:

| Asset                                     | Over the wire |
| ----------------------------------------- | ------------: |
| Home page HTML                            |        7.8 kB |
| Stylesheet (one file, whole site)         |        8.8 kB |
| My own JavaScript (six modules)           |        5.3 kB |
| Astro's view-transition router + prefetch |        6.0 kB |
| Fonts actually fetched (latin subsets)    |        ~40 kB |

No layout shift, no render-blocking third-party requests, and a first paint
bounded by the network rather than by anything the page is doing. The router is
the single largest script on the page, which is a fair trade for instant
navigation — and it is the only dependency in that list I did not write.

The interesting part is not the score. It is that the constraint — no framework
runtime — never once stopped me from building the thing I wanted. It only
forced me to know what the thing was first.
