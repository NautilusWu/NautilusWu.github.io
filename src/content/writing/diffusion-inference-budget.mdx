Every optimisation post about diffusion models opens with a number — 2× faster,
4× smaller — and almost none of them tell you what the baseline was doing with
its time. So before touching anything, I spent a day building a profile I
trusted. The result reorganised my entire plan.

The setup is deliberately boring: one consumer GPU, a 20-step sampler at
1024×1024, and a fixed seed so that every later comparison is against an
identical reference image rather than a vibe.

## Measure the loop, not the model

The mistake I made first was profiling a single forward pass. A sampler is not
one forward pass — it is _N_ of them plus a text encoder, a scheduler, and a
decode, and the fixed costs at the edges matter a lot more at 20 steps than
they do at 200.

```python
import torch

def profile_stages(pipe, prompt, steps=20):
    """Wall-clock each stage separately; CUDA is async, so synchronise."""
    timings = {}

    def stage(name):
        torch.cuda.synchronize()
        return _Timer(name, timings)

    with stage("encode"):
        cond = pipe.encode_prompt(prompt)

    latents = pipe.init_latents()
    with stage("denoise"):
        for t in pipe.scheduler.timesteps[:steps]:
            latents = pipe.step(latents, cond, t)

    with stage("decode"):
        image = pipe.decode(latents)

    return image, timings
```

The `torch.cuda.synchronize()` is the whole trick. Without it you are timing
kernel _launches_, which are nearly free, and the profile tells you that your
Python is slow — which it is, and which does not matter.

## The profile

| Stage            | Share of wall clock | Notes                                    |
| ---------------- | ------------------: | ---------------------------------------- |
| Text encode      |                  4% | Once per image; cacheable across a batch |
| Denoise (×20)    |                 84% | Attention-dominated at this resolution   |
| VAE decode       |                 11% | Single pass, but memory-bound            |
| Scheduler / glue |                  1% | Python, and genuinely irrelevant         |

Inside the denoise loop, attention was roughly 60% of the time and the
convolutional blocks about 30%, with the remainder in normalisation and
element-wise work that was almost entirely memory-bound.

> If 84% of your time is in one loop, a 40% win anywhere else is worth less
> than a 10% win inside it. Profiles are how you avoid being proud of the
> wrong number.

## What survived a quality check

I evaluated four changes against the fixed-seed baseline, comparing both a
perceptual metric and my own eyes at 100% zoom:

- **Attention kernel swap** — a fused scaled-dot-product path. ~22% faster
  end to end, bit-identical output within float tolerance. Kept, obviously.
- **8-bit weight-only quantization** — 31% less VRAM, a small latency win,
  and no difference I could find in the output. Kept.
- **4-bit weight-only quantization** — 52% less VRAM, but fine texture
  visibly degraded: skin and fabric went waxy. Rejected for this use, though
  it is the right answer if VRAM is the binding constraint.
- **Fewer steps** — trivially faster and trivially worse. Not an
  optimisation, just a different picture.[^1]

Stacked, the two changes I kept gave a 34% reduction in wall clock and a 31%
reduction in peak VRAM, with no measurable quality cost. That is a much less
exciting headline than 4×, and it is one I can defend.

## The part I would do differently

I should have written the fixed-seed comparison harness _first_. I built it
after rejecting 4-bit on a hunch, then had to go back and re-run everything to
get numbers I could put in a table. Measurement infrastructure always looks
like a detour until the moment you need to justify a decision.

[^1]:
    Reducing step count changes the sampling trajectory, so the output is a
    different image rather than a degraded version of the same one. It is not
    comparable to the other three rows and I should not have put it in the same
    list — but leaving it out would hide a real temptation.
